Glossário

TermoSignificado
RBACRole-Based Access Control — controle de acesso baseado em papéis
accessTokenToken de acesso Okta enviado no header Authorization. Usado pelo BFF para chamar /userinfo e validar o usuário.
RolePapel do usuário (ex: sales_manager, seller, mfs_employee)

Contexto

O Hyperfront atualmente possui autenticação via Okta (PKCE flow) com middleware global que apenas diferencia usuários autenticados vs. não autenticados. Não há qualquer controle de autorização baseado em papéis.

  • Todos os usuários autenticados enxergam o mesmo menu lateral
  • Todas as rotas são acessíveis por qualquer usuário logado
  • Não existe verificação de roles no middleware, sidebar ou componentes
  • O Okta já retorna o array roles no endpoint /userinfo e no client-side via getUser() — mas ele nunca é utilizado

O endpoint /userinfo do Okta retorna o array roles com os papéis do usuário:

{
  "sub": "user@company.com",
  "roles": ["sales_manager"],
  "email": "user@company.com"
}

Solução Proposta

Arquitetura RBAC (Role-Based Access Control) puro — sem camada de permissões, sem MongoDB, sem API intermediária. O array roles[] obtido via Okta /userinfo (server) e oktaAuth.getUser() (client) é a única fonte de autorização em todas as camadas: frontend, middleware Nuxt e BFF (00-authGuardHandler.ts).

Implementação

Passo 1: Cache + UserInfo BFF

Arquivo: server/utils/oktaUserinfo.ts (novo)

Utilitário server-side que chama o endpoint /userinfo do Okta com o accessToken para obter as roles do usuário. Inclui cache in-memory keyed por jti (JWT ID) com TTL = exp do token. Max 1000 entradas, evicção LRU.

// server/utils/oktaUserinfo.ts
export async function getUserRoles(accessToken: string): Promise<string[]> {
  const payload = JSON.parse(atob(accessToken.split('.')[1]))
  const { jti, exp } = payload

  // Cache hit
  const hit = cache.get(jti)
  if (hit && hit.expiresAt > Date.now()) return hit.roles

  // Cache miss → Okta /userinfo
  const issuer = useRuntimeConfig().public.okta.issuer
  const data = await $fetch<{ roles: string[] }>(`${issuer}/v1/userinfo`, {
    headers: { Authorization: `Bearer ${accessToken}` }
  })

  const roles = data.roles ?? []

  // Cache com TTL do token
  if (jti && exp * 1000 > Date.now()) {
    if (cache.size >= MAX_SIZE) cache.delete(cache.keys().next().value)
    cache.set(jti, { roles, expiresAt: exp * 1000 })
  }

  return roles
}

🗝️ Cache por jti

Key = jti do accessToken. TTL = exp - now. Se o token expirar, o cache expira junto.

🔒 Okta valida o token

Diferente de decodificar JWT sem verificar assinatura, o /userinfo só retorna dados se o token for válido.

📦 Sem dependências

Usa atob() para extrair jti/exp e $fetch (nativo Nuxt) para chamar Okta.

Passo 3: Auth Store — extrair roles do Okta

Arquivo: features/auth/stores/auth.ts (modificar)

O que muda:

  1. Adicionar roles: ref<string[]>([]) — extraído de oktaAuth.getUser()
  2. Em handleOktaAuthState(): após oktaAuth.getUser(), extrair roles do objeto claims retornado
  3. Adicionar helpers no return: hasRole(role): boolean, hasAnyRole(...roles): boolean, hasAllRoles(...roles): boolean

// Dentro de handleOktaAuthState(), após oktaAuth.getUser()
const claims = await oktaAuth.getUser()
roles.value = Array.isArray(claims.roles) ? claims.roles : []

// Helpers no return
const hasRole = (role: string) => roles.value.includes(role)
const hasAnyRole = (...check: string[]) => check.some(r => roles.value.includes(r))
const hasAllRoles = (...check: string[]) => check.every(r => roles.value.includes(r))

⚡ Mesmo pattern do código existente

Passo 4: Composable useRoles

Arquivo: shared/composables/useRoles.ts (novo)

Wrapper fino sobre a auth store, mesmo padrão do useAuth existente.

export const useRoles = () => {
  const authStore = useAuthStore()

  const hasRole = (role: string) => authStore.hasRole(role)
  const hasAnyRole = (...roles: string[]) => authStore.hasAnyRole(...roles)
  const hasAllRoles = (...roles: string[]) => authStore.hasAllRoles(...roles)

  return {
    hasRole,
    hasAnyRole,
    hasAllRoles,
    roles: computed(() => authStore.roles),
  }
}

Passo 9: BFF Guard — server middleware

Arquivo: server/middleware/00-authGuardHandler.ts (novo)

Server middleware do Nuxt que roda antes de qualquer handler. Lê o accessToken do header Authorization, chama getUserRoles() (que valida via Okta /userinfo com cache) e verifica se o usuário tem role permitida. Não usa header extra — o Authorization já está presente em toda request.

import { getUserRoles } from '~/server/utils/oktaUserinfo'
import { Roles } from '~/shared/constants/roles'

// Mapa de rotas BFF → roles permitidas
const BFF_ROUTE_ROLES: Record<string, string[]> = {
  'GET /api/auth/brokers':          [Roles.SALES_MANAGER, Roles.ADMIN, Roles.SELLER, Roles.STANDALONE_SELLER, Roles.MFS_EMPLOYEE],
  'GET /api/auth/broker-contacts':   [Roles.SALES_MANAGER, Roles.ADMIN, Roles.SELLER, Roles.STANDALONE_SELLER, Roles.MFS_EMPLOYEE],
  'POST /api/deals':                  [Roles.SALES_MANAGER, Roles.ADMIN, Roles.SELLER, Roles.MFS_EMPLOYEE],
  'PUT /api/deals/assignments':       [Roles.SALES_MANAGER, Roles.ADMIN],
  // ... demais rotas
}

export default defineEventHandler(async (event) => {
  const auth = getHeader(event, 'authorization')
  if (!auth?.startsWith('Bearer ')) throw createError({ statusCode: 401 })

  const roles = await getUserRoles(auth.slice(7))
  event.context.roles = roles // disponível para handlers downstream

  const path = event.path.replace('/api/', '')
  const key = `${event.method} /${path}`

  const guard = BFF_ROUTE_ROLES[key]
  if (guard && !guard.some(r => roles.includes(r))) {
    throw createError({ statusCode: 403, statusMessage: 'Forbidden' })
  }
})

🔐 Usa Authorization existente

Sem header extra — o Bearer token já está presente em toda request. BFF chama /userinfo do Okta para validar.

📋 Cache com TTL do token

getUserRoles() cacheia por jti com expiração = exp do token. Cache miss = chamada ao Okta.

🛡️ Okta valida a assinatura

Diferente de decodificar JWT localmente, o /userinfo só responde se o token for válido e não expirado.

Segurança

Defense in Depth

CamadaO que fazNível de Confiança
Frontend (Vue)UX: esconde rotas/botões que o usuário não pode usarBaixo
Middleware NuxtUX: bloqueia navegação para páginas não autorizadasMédio
BFF — 00-authGuardHandler.tsAutorização real: valida token via Okta /userinfo + cache, rejeita requests não autorizadas antes de qualquer handlerAlto
Backend (deal-bs)Segurança legacy: valida token Okta (defense in depth)Alto
⚠ Importante: O RBAC no frontend (Vue + middleware Nuxt) é camada de usabilidade. A autorização real está no BFF — 00-authGuardHandler.ts — que chama /userinfo do Okta, cacheia por jti, e valida as roles antes de qualquer request chegar ao backend deal-bs.
