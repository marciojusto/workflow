## 1. Root Cause Analysis

### 1.1 The Problem

Miles backend desativou o campo `enumGroupId` (Houssem: "Disabled enumID on Miles"). O `resolveEntityGroupId()` em `partyMapper.ts` retorna `null` quando todos os campos enum estão ausentes, e NÃO havia lógica de fallback para inferir o tipo de entidade a partir dos dados disponíveis.

### 1.2 Failure Chain

```
1. Miles API retorna customer SEM legalEntity.enumGroupId / enumId
2. resolveEntityGroupId() retorna null ─ sem fallback inference
3. Vários callers ignoram a centralized resolver e leem raw:
   - buildProposalIndOrST (L924): customerObj?.legalEntity?.enumGroupId
   - buildProposalOrg (L1036): customerObj?.legalEntity?.enumGroupId
   - mapPartyDetailsSimulation (L550): source.legalEntity?.enumGroupId
   - dealPayloadBuilder.ts (L242): getLabelClientType(String(null)) → undefined
4. Party guardada no MongoDB com typeEnumId=null e customer vazio
5. Na re-edição: mapPartyByType() vê typeEnumId=null → initMinimalClientParty()
6. UI mostra dados do cliente vazios
```

**Current (L599-635):**

```typescript
function resolveEntityGroupId(customer: any): string | null {
  if (!customer) return null;
  const legalEntity = customer?.legalEntity ?? null;
  const legalEntityType = customer?.legalEntityType ?? null;
  const enumGroupId = /* ... checks enumGroupId ... */;
  if (enumGroupId) return String(enumGroupId);

  /* ... maps known enumId values ... */

```

**New:** Add fallback inference AFTER enum-based detection fails:
```typescript
  // --- (existing enum checks above) ---
  const enumId = legalEntity?.enumId ?? legalEntityType?.enumId ?? legalEntityType?.enumID ?? null;
  if (!enumId) {
    // --- FALLBACK: infer from data shape when enum IDs are absent ---
    const hasIndividualPerson = !!(customer?.individualPerson);
    const hasTradingName = !!(customer?.tradingName);
    const hasVatNumber = !!(customer?.vatNumber);

    // Sole trader: has both individualPerson AND (tradingName or vatNumber)
    if (hasIndividualPerson && (hasTradingName || hasVatNumber)) {
      return EntityGroup.SOLETRADER;
    }
    // Organization: has tradingName or vatNumber, no individualPerson
    if ((hasTradingName || hasVatNumber) && !hasIndividualPerson) {
      return EntityGroup.ORGANIZATION;
    }
    // Individual: has individualPerson but no tradingName/vatNumber
    if (hasIndividualPerson) {
      return EntityGroup.INDIVIDUAL;
    }
    return null;
  }
```

## 5. Code Principles Adherence

### 5.1 DRY (Don't Repeat Yourself)

| Before | After |
|--------|-------|
| `resolveEntityGroupId()` centraliza lógica de enum mas NÃO é usado por todos os callers | ✅ Todos os 4 bypass paths (L550, L924, L1036, L242) passam a usar a resolução centralizada |
| `buildProposalIndOrST` e `buildProposalOrg` têm código duplicado para ler `customerObj?.legalEntity?.enumGroupId` | ✅ Ambos passam a usar parâmetro recebido |
| `mapPartyDetailsSimulation` reimplementa raw read | ✅ Usa `resolveEntityGroupId()` |

**Resultado:** Elimina 4 leituras raw duplicadas. A inferência de tipo fica num único sítio — violações DRY corrigidas.

### 5.2 KISS (Keep It Simple)

| Proposta | Análise |

| Fix L924 (usar param existente) | ✅ **SIMPLES** — substituição de 1 linha |
| Fix L1036+1129 (add param) | ✅ **SIMPLES** — 1 novo param, mesma pattern de `buildProposalIndOrST` |
| Fix L550 (usar resolver) | ✅ **SIMPLES** — 2 linhas |

**Complexidade total:** ~20 linhas novas, ~10 alteradas. Cada change é uma substituição direta ou adição simples.

### 5.3 YAGNI (You Aren't Gonna Need It)

| Proposta | YAGNI OK? |
|----------|-----------|
| Fallback inference | ✅ **NECESSÁRIO** — sem ele, `resolveEntityGroupId()` retorna null, causando o bug |

### 5.4 SOLID Principles

| Principle | Análise |
|-----------|---------|
| **S**ingle Responsibility | ✅ `resolveEntityGroupId()` mantém a responsabilidade única de determinar o entity group; o fallback inference é uma extensão natural. `buildProposalIndOrST`/`buildProposalOrg` mantêm a sua responsabilidade de mapear proposal data. |
| **O**pen/Closed | ✅ A função está **aberta para extensão** (fallback inference adicionado) mas **fechada para modificação** (lógica enum existente inalterada). |
| **L**iskov Substitution | N/A — sem hierarquia de tipos envolvida. |
| **I**nterface Segregation | ✅ O parâmetro `customer` object é coeso; `buildProposalOrg` recebe apenas `legalEntityGroupId` (string), não o objeto `customerObj` inteiro para resolver o tipo — isto **reduz o acoplamento**. |
| **D**ependency Inversion | ✅ `resolveEntityGroupId()` depende de uma abstração (o contrato de dados BS), não de implementações concretas. |

## 6. Acceptance Criteria & Verification

### AC1: Fallback inference funciona
```
Given: Miles response sem enumGroupId e enumId
When: resolveEntityGroupId(customer) é chamado
Then: Retorna EntityGroup baseado em individualPerson/tradingName/vatNumber
```
- Individual: `{ individualPerson: { firstName: "John" } }` → `"2050"`
- Organization: `{ tradingName: "Acme", vatNumber: "BE123" }` → `"2051"`
- Sole Trader: `{ individualPerson: { firstName: "John" }, tradingName: "John Co" }` → `"2052"`

### AC2: Proposal path usa resolved value
```
Given: buildProposalParty é chamado com Miles response sem enumGroupId
When: Mapeia customer data
Then: typeEnumId no resultado NÃO é null
```

### AC3: Party details path usa resolver
```
Given: GET /api/parties retorna customer sem enumGroupId
When: mapPartyDetails é chamado
Then: enumGroupId resolved via resolveEntityGroupId(), não raw read
```

### AC4: Deal payload trata null
```
Given: customer.sem enumGroupId
When: buildDealPayload é chamado
Then: client_type no payload é null (não "null" string nem undefined)
```

### AC5: Regressão — fluxos existentes intactos
```
Given: Miles response COM enumGroupId
When: Qualquer caminho (simulation, proposal, details)
Then: Comportamento IDÊNTICO ao anterior (enum detection corre primeiro)
```
